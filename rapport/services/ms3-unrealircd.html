UnrealIRCd 3.2.8.1 — Backdoor Command Execution

Porte dérobée insérée dans l'archive officielle compromise — exploitation manuelle réussie, module Metasploit en échec dans ce labo

Service / PortIRC (UnrealIRCd) — port 6697
CibleMetasploitable 3 — 172.28.128.3
CVECVE-2010-2075
RésultatExécution de commande confirmée (shell boba_fett) — à la main uniquement
Testé parKAGBAHINTO Jules

1. Identification

Le port 6697 est conventionnellement réservé à IRC-over-TLS, mais une tentative de handshake SSL échoue immédiatement avec une erreur caractéristique d'un serveur qui ne parle pas réellement TLS sur ce port, confirmée par une connexion en clair qui obtient une réponse IRC normale (capture a).

2. Méthode d'identification de la CVE et du module

searchsploit unrealircd puis search unreal dans msfconsole trouvent exploit/unix/irc/unreal_ircd_3281_backdoor. info confirme CVE-2010-2075 (capture b).

Mécanisme. Entre novembre 2009 et juin 2010, l'archive officielle Unreal3.2.8.1.tar.gz a été compromise sur les miroirs de téléchargement — une porte dérobée a été insérée directement dans le code source distribué. Toute ligne reçue par le serveur et commençant par la chaîne magique AB; est passée intégralement à system(), avant même d'être interprétée comme une commande IRC. Ni authentification ni enregistrement NICK/USER requis.

3. Démarche d'exploitation

Le module détecte correctement la cible comme vulnérable ("UnrealIRCd detected after registration"), mais exploit -z échoue systématiquement : "Exploit completed, but no session was created" — testé avec et sans AutoCheck, et avec quatre payloads différents, toujours le même résultat (capture c).

La lecture du code source du module révèle la cause : exploit() envoie la charge puis appelle disconnect immédiatement, sans aucune pause. Or le serveur répond d'abord par un NOTICE AUTH :*** Looking up your hostname... — une résolution DNS inverse bloquante qui retarde d'environ 30 secondes le moment où il reprend la lecture du buffer contenant AB;.... L' option wfsDelay = 30 du module n'agit qu'après la fin de exploit(), pas avant — elle ne protège pas contre cette fermeture prématurée.

En reproduisant l'envoi à la main et en gardant simplement la socket ouverte 35 secondes avant de la fermer, la commande s'exécute parfaitement (capture d), confirmé par un shell interactif complet rejouant le payload exact que Metasploit aurait dû envoyer (capture e).

4. Preuve d'accès obtenu

Accès non privilégié confirmé (uid=1121(boba_fett)) — cohérent avec 'Privileged' => false annoncé par le module lui-même, UnrealIRCd ne tourne pas en root sur cette installation. Piste de post-exploitation non explorée ici : boba_fett appartient au groupe docker (capture d).

5. Remédiation

RECOMMANDATIONS
  • Vérifier systématiquement le hash/la signature d'une archive tierce avant déploiement — c'est exactement ce contrôle qui aurait détecté le tarball compromis entre 2009 et 2010.
  • Mettre à jour UnrealIRCd vers une version post-2010, toutes compilées depuis du code source propre.
  • Surveiller les sommes de contrôle officielles de tout paquet tiers avant mise en production, pas seulement pour IRC.
