PostgreSQL 8.3.1 — RCE via bibliothèque UDF compilée

Deux tentatives manuelles réfutées avant de comprendre le vrai mécanisme : compilation d'une .so avec le bon magic block

CibleMetasploitable 1 — 192.168.56.102

Note réseau. Cette page utilise le réseau de Josaphat (vboxnet0) : cible 192.168.56.102, Kali 192.168.56.1. Côté Jules, le même service est sur 172.28.128.4.

1. Identification

Le scan de reconnaissance identifie PostgreSQL 8.3.1. Les identifiants par défaut postgres:postgres fonctionnent et donnent un compte superuser — condition nécessaire pour la suite (capture a).

2. Méthode d'identification de la CVE et du module

Tentative n°1 — COPY ... TO PROGRAM échoue (syntax error) : cette syntaxe a été introduite en PostgreSQL 9.3 (2013), la cible est en 8.3.1 (2008), largement antérieure. Tentative n°2 — créer une fonction SQL pointant vers system() de la libc échoue aussi (missing magic block) : PostgreSQL exige depuis la 8.2 qu'une bibliothèque C chargée déclare un PG_MODULE_MAGIC, que la libc brute n'a pas (capture b). Les deux échecs sont de vraies pistes réfutées, pas des impasses ignorées.

Recherche du vrai mécanisme via info sur le module Metasploit dédié (capture c) :

Mécanisme réel. CVE-2007-3280. Le module ne charge pas une lib système quelconque (ce qui expliquait les deux échecs précédents) : il compile sa propre bibliothèque partagée, correctement marquée avec PG_MODULE_MAGIC pour la version exacte du serveur cible, l'écrit dans /tmp (accessible en écriture par le compte postgres) via les fonctions de large objects, puis la charge comme fonction UDF pour exécuter le payload.

3. Démarche d'exploitation

Resource script via msfconsole : chargement du module, configuration des options, puis exploit -z (capture d). La ligne Uploaded as /tmp/wltnxZOA.so confirme exactement le mécanisme lu dans la description du module : une .so compilée à la volée, déposée dans /tmp.

4. Preuve d'accès obtenu

sessions -i 1 -c id confirme le shell en tant que postgres. Pas root : l'élévation de privilèges sera une étape distincte.

5. Remédiation

RECOMMANDATIONS
  • Changer le mot de passe par défaut (postgres:postgres) — cause racine de l'accès initial.
  • Mettre à jour PostgreSQL : la 8.3.1 (2008) est très obsolète.
  • Restreindre les droits du compte système postgres : il ne devrait pas pouvoir écrire dans des répertoires partagés comme /tmp qui servent ensuite de point de chargement pour des bibliothèques UDF arbitraires (cœur de CVE-2007-3280).
  • Restreindre l'accès réseau à PostgreSQL (pg_hba.conf, pare-feu).
  • Révoquer le statut superuser des comptes applicatifs dès que possible.
