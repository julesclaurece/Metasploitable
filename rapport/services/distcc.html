DistCC Daemon — RCE

Exécution de commande à distance sans authentification, avec diagnostic d'une ACL réseau bloquante

Service / Portdistccd — port 3632
CibleMetasploitable 1 — 172.28.128.4
CVECVE-2004-2687
RésultatShell utilisateur daemon (pas root direct — voir Remédiation)
Testé parKAGBAHINTO Jules

1. Identification

Le scan de reconnaissance identifie un démon distccd en écoute sur le port 3632. Le script NSE dédié (distcc-cve2004-2687) confirme directement la vulnérabilité et exécute même id pour le prouver (capture a) — ce résultat suppose que le réseau d'où on scanne est déjà autorisé par l'ACL du démon. Lors du tout premier contact avec ce service, ce n'était pas le cas (voir section 3) : le script ne remontait alors rien de concluant, le temps de diagnostiquer et corriger cette ACL.

2. Méthode d'identification de la CVE et du module

searchsploit distcc confirme qu'un exploit connu existe, puis search distcc dans msfconsole donne le chemin exact du module : exploit/unix/misc/distcc_exec (capture b).

info sur ce module donne, dans sa section References, CVE-2004-2687 (capture c). distccd (démon de compilation distribuée) exécute, par conception, toute commande de compilation reçue sans authentification — le seul garde-fou prévu est une liste blanche d'IP/réseaux autorisés (--allow), fixée au démarrage du démon.

3. Démarche d'exploitation

Sonder le protocole à la main — avant tout outillage, un test manuel du protocole distcc (handshake minimal DIST00000001) permet de vérifier si l'ACL du démon bloque notre réseau d'attaque, sans construire un payload complet (capture d).

Le build par défaut de cette VM autorise seulement 192.168.0.0/16, 10.0.0.0/8 et 172.16.0.0/16 — notre réseau de labo (172.28.128.0/24) n'y figure pas. Correctif (console VM) : la liste --allow est codée en dur dans /etc/init.d/distcc (pas dans /etc/default/distcc comme son nom le suggérerait) — édition du script, puis relance forcée du démon, puisque restart/stop sont des no-op volontaires dans ce build (capture e).

Exploiter — une fois l'ACL corrigée, démarche interactive dans msfconsole : use du module puis configuration des options (RHOSTS, PAYLOAD, LHOST, LPORT) (capture f), puis exploit -z déclenche l'attaque (capture g).

4. Preuve d'accès obtenu

sessions -i 1 -c id confirme l'accès ; l'utilisateur obtenu est daemon (uid=1), conforme au --user daemon passé au démarrage du service — pas root, contrairement à la backdoor vsftpd.

5. Remédiation

RECOMMANDATIONS
  • Ne jamais exposer distccd sur un réseau non totalement maîtrisé — ce service est conçu pour un usage interne (ferme de compilation), pas pour être accessible depuis l'extérieur.
  • Si l'exposition est nécessaire, restreindre l'ACL --allow au strict sous-réseau des machines de compilation autorisées, jamais à des plages RFC1918 larges par défaut.
  • Préférer un tunnel SSH ou un VPN pour la distribution de compilation à distance, plutôt que d'exposer le protocole distcc directement.
  • Même si l'accès obtenu ici n'est que daemon (pas root), ce compte reste un point d'entrée exploitable pour une élévation de privilèges ultérieure — corriger la cause racine (exposition du service) plutôt que de compter sur le cloisonnement des droits.
