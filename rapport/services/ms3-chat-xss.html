Chat App — XSS stockée

Injection de script exécutée automatiquement chez tous les clients connectés, cookie de session non protégé

Service / PortHTTP — port 80, /chat/
CibleMetasploitable 3 — 172.28.128.3
CVE— (appli maison modifiée depuis un tutoriel public)
RésultatXSS stockée confirmée, vol de session possible (cookie sans HttpOnly)
Testé parKAGBAHINTO Jules

1. Identification

Un commentaire dans le code source HTML révèle l'origine de l'appli — un tutoriel public de chat simple, explicitement modifié par les auteurs de MS3 (capture a). Indice fort qu'une faille y a été introduite volontairement par rapport au tutoriel d'origine.

2. Démarche — trouver les vrais endpoints

Deviner les noms de fichiers à partir du tutoriel original (chat.php, send.php...) n'a rien donné. Un vrai scan gobuster trouve post.php — mais une première tentative de login échoue à révéler la page de chat.

Piège rencontré. Soumettre le formulaire de login sans suivre la redirection (-L) ni conserver les cookies (-c/-b) ne montre que le même formulaire en boucle. En mode verbeux, la vraie réponse est un 302 Found qui pose un cookie et redirige — sans ces deux options curl, la page de chat réelle n'est jamais vue.

Une fois corrigé (cookie jar + -L), la vraie page de chat révèle son JavaScript : les messages sont postés sur post.php (paramètre text, pas message) et le log est lu via read_log.php, rafraîchi toutes les secondes pour tous les clients connectés (capture b).

3. Preuve d'accès — XSS stockée confirmée

Un payload <script> posté via post.php est inséré tel quel, sans échappement, dans la sortie de read_log.php — injectée directement dans le DOM côté client, exécutée automatiquement chez tout utilisateur ayant la page ouverte, sans action de sa part (capture c).

Impact réel. Le cookie PHPSESSID n'a pas l'attribut HttpOnly — document.cookie est donc accessible depuis un payload JavaScript injecté. Un vrai payload (pas juste alert()) pourrait exfiltrer la session de n'importe quel autre utilisateur du chat.

Point de comparaison : le champ name utilisé au login, lui, échappe correctement les entrées (<b> au lieu de HTML actif) — la faille est précise, limitée au chemin post.php → read_log.php, pas généralisée à toute l'appli.

4. Remédiation

RECOMMANDATIONS
  • Échapper systématiquement les données utilisateur avant insertion dans le HTML retourné par read_log.php (htmlspecialchars(), déjà correctement appliqué pour le champ name).
  • Ajouter l'attribut HttpOnly sur le cookie de session — empêche le vol de session même en cas de XSS résiduelle ailleurs.
  • Revoir la politique CORS : Access-Control-Allow-Origin: * combiné à Access-Control-Allow-Credentials: true est une configuration dangereuse.
  • Mettre en place une Content-Security-Policy restrictive, en défense en profondeur.
