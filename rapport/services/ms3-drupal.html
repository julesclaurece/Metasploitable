Drupal 7.5 — Drupalgeddon2 Forms API Injection

Vulnérabilité confirmée et point d'entrée vulnérable atteint, exploitation bloquée par une erreur PHP diagnostiquée précisément

Service / PortHTTP (Drupal 7.5) — port 80, /drupal/
CibleMetasploitable 3 — 172.28.128.3
CVECVE-2018-7600 (« Drupalgeddon2 »)
RésultatBloqué — vulnérabilité confirmée, cause du blocage diagnostiquée précisément
Testé parKAGBAHINTO Jules
Résultat non abouti, documenté volontairement. Comme pour Samba sur cette même cible, aucun accès final obtenu ici — mais la cause du blocage a été tracée jusqu'à une ligne de code précise, pas laissée comme un simple "ça ne marche pas".

1. Identification

Le script NSE de reconnaissance révèle directement le contenu du webroot (listing de répertoire Apache activé) : quatre applis distinctes exposées (chat/, drupal/, payroll_app.php, phpmyadmin/). Le fichier CHANGELOG.txt de Drupal confirme la version exacte : Drupal 7.5 (2011), largement antérieure à la version corrigée 7.58 (capture a).

2. Méthode d'identification de la CVE et du module

searchsploit drupal 7 puis search drupal 7 dans msfconsole trouvent le module exploit/unix/webapp/drupal_drupalgeddon2. info dessus confirme CVE-2018-7600 (capture b).

Mécanisme. La Forms API de Drupal construit les formulaires sous forme de tableaux PHP imbriqués, où des clés spéciales (#post_render, #markup...) contrôlent le rendu. La faille permet d'injecter ces clés spéciales dans une requête utilisateur normale : Drupal traite alors #post_render comme un callback PHP à exécuter sur #markup, sans vérifier que ce callback vient bien du code légitime — exécution de code arbitraire.

3. Démarche d'exploitation et diagnostic

Premier essai via Metasploit : LHOST auto-réglé sur une IP hors du réseau du labo (piège rencontré, corrigé en le forçant explicitement). Une fois corrigé, toujours aucune session malgré 3 techniques d'injection PHP tentées en interne par le module (printf, assert/eval, passthru), ni avec un payload de commande directe sans connexion retour (capture c).

Plutôt que de deviner pourquoi, lecture du code source du module (déjà installé localement) pour comprendre exactement les deux requêtes HTTP qu'il envoie (POST sur user/password avec les clés Forms API injectées, puis POST sur file/ajax/... avec le form_build_id récupéré), puis reproduction manuelle exacte avec curl (capture d).

Diagnostic précis : la requête atteint bien la fonction vulnérable (file_ajax_upload(), confirmée par l'erreur PHP elle-même citant le code source officiel de Drupal) — le chemin de code vulnérable est correctement déclenché. Mais le tableau de formulaire reconstruit entre les deux requêtes (via le cache identifié par form_build_id) ne contient pas la clé #value attendue à ce stade — l'injection n'a pas "survécu" à la sérialisation du cache de formulaire sur cette install précise.

4. Conclusion

Vulnérabilité confirmée à tous les niveaux (version, CVE, point d'entrée vulnérable atteint), mais exploitation non aboutie avec la technique standard — cause tracée jusqu'à la ligne de code exacte qui échoue, pas un simple constat d'échec.

5. Remédiation

RECOMMANDATIONS
  • Mettre à jour Drupal vers 7.58 ou supérieur — patch officiel SA-CORE-2018-002.
  • Valider strictement les clés de tableau autorisées dans les données utilisateur avant fusion dans un tableau de rendu Forms API — cause racine de la CVE.
  • Surveiller les requêtes vers user/password et file/ajax/* contenant des paramètres de formulaire inhabituels.
