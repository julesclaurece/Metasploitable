Payroll App — Injection SQL

Contournement d'authentification et exfiltration complète d'une table de données sensibles via une requête SQL non échappée

Service / PortHTTP — port 80, /payroll_app.php
CibleMetasploitable 3 — 172.28.128.3
CVE— (appli maison, faille de code applicative)
Résultat15 employés exfiltrés (salaires inclus), sans authentification valide
Testé parKAGBAHINTO Jules

1. Identification

Repérée dans le listing du webroot (recon partagée avec Drupal). Appli minimaliste : un formulaire de login (user/password) qui se poste lui-même, en PHP 5.4.5 (capture a) — ancien, cohérent avec une appli jamais mise à jour.

2. Démarche d'exploitation — injection SQL

Pas de CVE à chercher ici — appli maison, pas un produit connu. Hypothèse testée en premier : identifiants faibles. admin:admin fonctionne (login accepté), mais la table retournée est vide. Hypothèse suivante : injection SQL classique sur les deux champs (capture b) — la table entière est retournée.

Mécanisme. La requête est probablement WHERE user='$user' AND password='$password', avec les valeurs POST concaténées directement sans échappement. En remplaçant les deux champs par ' OR '1'='1, la clause devient toujours vraie (WHERE user='' OR '1'='1' AND password='' OR '1'='1') et retourne toutes les lignes, peu importe les vraies valeurs stockées.

Confirmation que l'injection doit toucher les deux champs : injecter seulement user avec un mot de passe quelconque donne une table vide — logique, AND est prioritaire sur OR en SQL, donc neutraliser un seul côté de la clause ne suffit pas. Un guillemet seul casse la requête (page totalement vide), signe d'une concaténation directe sans échappement ni requête préparée.

3. Preuve d'accès obtenu

Dump complet de la table : 15 employés, avec leur salaire — données clairement sensibles pour une appli RH (capture c). À noter : le compte chewbacca trouvé par énumération Samba (page dédiée) apparaît aussi ici comme employé — probablement un fil conducteur volontaire du labo sur plusieurs services, pas une coïncidence technique.

4. Remédiation

RECOMMANDATIONS
  • Utiliser des requêtes préparées (prepared statements) partout où une entrée utilisateur entre dans une requête SQL — élimine la classe entière de vulnérabilité, pas juste ce cas précis.
  • Ne jamais construire une requête SQL par concaténation de chaînes avec des données POST brutes.
  • Mettre à jour PHP (5.4.5 est hors support depuis des années) et le serveur SQL sous-jacent.
  • Chiffrer ou masquer les données sensibles (salaires) même en cas d'accès légitime, par défense en profondeur.
