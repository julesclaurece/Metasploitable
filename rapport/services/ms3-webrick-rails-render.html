WEBrick / Rails — Dynamic Render File Upload

Appli Ruby maison vulnérable à un rendu de template contrôlé par l'utilisateur — exploitation reproduite jusqu'au rendu, bloquée par un problème de permissions distinct de la faille

Service / PortHTTP (WEBrick 1.3.1, Rails 4.2.4) — port 3500, route /readme
CibleMetasploitable 3 — 172.28.128.3
CVECVE-2016-0752
RésultatVulnérabilité confirmée, rendu du fichier contrôlé obtenu — exécution de code bloquée par un problème de permissions filesystem indépendant
Testé parKAGBAHINTO Jules

1. Identification

Le port est trouvé fermé au premier scan — le service n'avait jamais été démarré dans cette instance de VM (pas de job upstart associé). Relancé manuellement via l'accès shell déjà obtenu sur la cible (backdoor UnrealIRCd, voir page dédiée), après avoir contourné un fichier de verrou (pid) périmé (capture a).

2. Méthode d'identification de la CVE et du module

Pas de produit connu à chercher directement — appli Rails maison. La lecture du code source (accès shell déjà disponible) révèle le motif exact qui a guidé la recherche : render template où template provient de params[:os] sans aucune validation (capture b).

Mécanisme. Rails (jusqu'à 5.0.0.beta1.1) traite toute chaîne passée à render contenant un / comme un nom de template à rechercher dans app/views/. Ce lookup reste sandboxé dans ce répertoire, mais le sandbox est contournable par traversée (../). Combiné à la fuite prévisible du chemin d'un fichier temporaire uploadé (Rails affiche ce chemin dans ses pages d'erreur très verbeuses en développement), un attaquant peut faire exécuter comme template ERB un fichier qu'il contrôle entièrement.

3. Démarche d'exploitation

Deux étapes. D'abord, un upload multipart contenant du code ERB déclenche une erreur de template manquant qui révèle le chemin exact du fichier temporaire créé sur le serveur (capture c). Vérifié sur la cible que ce fichier reste présent après la réponse — pas de nettoyage automatique avec cette version de Rack.

Ensuite, passer ce chemin en traversée relative (../../../../tmp/..., pour remonter de app/views/ jusqu'à la racine) au lieu d'un chemin absolu fait basculer l'erreur de ActionView::MissingTemplate à Errno::EACCES : la preuve que le fichier a été localisé et que son rendu a commencé (capture d).

Le module Metasploit officiel va plus loin dans l'automatisation (upload + tentative de téléchargement du stage) mais échoue pour la même raison sous-jacente (capture e).

4. Preuve d'accès obtenu

Pas d'exécution de code confirmée dans cette session. La preuve obtenue est partielle mais sans ambiguïté : le changement d'erreur (capture d) démontre que le fichier contrôlé par l'attaquant a été localisé et que son traitement comme template a commencé — l'étape qui suit (rendu effectif du contenu ERB injecté) est bloquée par un problème de permissions filesystem propre à cette instance (droits chewbacca vs boba_fett sur le cache des assets), pas par la faille elle-même.

5. Remédiation

RECOMMANDATIONS
  • Mettre à jour Rails au-delà de la version patchée (5.0.0.beta1.1), qui corrige la normalisation des arguments de render à la source.
  • Ne jamais passer une chaîne contrôlée par l'utilisateur directement à render — utiliser une liste blanche explicite de valeurs autorisées.
  • Restreindre les permissions d'écriture sur les répertoires de cache applicatifs à l'utilisateur qui exécute réellement le service.
