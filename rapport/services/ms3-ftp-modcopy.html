ProFTPD 1.3.5 — mod_copy RCE

Copie de fichier côté serveur sans authentification, menant à l'exécution de code via le webroot

Service / PortFTP (ProFTPD) — port 21
CibleMetasploitable 3 — 172.28.128.3
CVECVE-2015-3306
RésultatShell utilisateur www-data
Testé parKAGBAHINTO Jules

1. Identification

Le scan de reconnaissance identifie ProFTPD en version 1.3.5. Un test de login anonyme est fermé (530 Login incorrect.) — piste éliminée (capture a).

2. Méthode d'identification de la CVE et du module

searchsploit proftpd 1.3.5 confirme plusieurs exploits connus, mais ce sont des chemins Exploit-DB, pas un module Metasploit utilisable. search proftpd dans msfconsole remonte plusieurs résultats pour d'autres versions (1.2-1.3.0, 1.3.2rc3-1.3.3b, 1.3.3c...) ; un seul correspond à la version 1.3.5 exacte : exploit/unix/ftp/proftpd_modcopy_exec (capture b).

info sur ce module donne, dans sa section References, CVE-2015-3306 (capture c). Le module mod_copy expose les commandes FTP SITE CPFR/SITE CPTO sans vérifier l'état d'authentification de la session — n'importe quel client connecté peut faire copier un fichier lisible par le process FTP vers n'importe quel chemin accessible en écriture par ce même process, y compris le webroot Apache, d'où RCE possible via un payload PHP.

3. Démarche d'exploitation

Preuve de concept manuelle — sur une connexion FTP fraîche, sans aucun login, les commandes SITE CPFR/SITE CPTO passent directement : copie de /etc/passwd vers un fichier temporaire, confirmant la faille avant tout outillage (capture d).

Exploiter — démarche interactive dans msfconsole : chargement du module et configuration des options, en particulier SITEPATH qui doit pointer sur le vrai webroot (/var/www/html, pas la valeur par défaut du module qui échoue) (capture e), puis exploit -z déclenche l'attaque (capture f).

4. Preuve d'accès obtenu

sessions -i 1 -c id confirme l'accès sous www-data, le compte d'exécution d'Apache/PHP.

Le message final du module (Exploit aborted ... Failure executing payload / no session was created) est trompeur — la session s'ouvre bien juste avant, le module échoue seulement sur son nettoyage HTTP après coup. Toujours vérifier avec sessions -l plutôt que de se fier au message de fin.

5. Remédiation

RECOMMANDATIONS
  • Mettre à jour ProFTPD vers une version postérieure corrigeant CVE-2015-3306, ou désactiver le module mod_copy s'il n'est pas utilisé.
  • Vérifier que toutes les commandes SITE exposées par les modules ProFTPD respectent bien l'état d'authentification de la session, pas seulement mod_copy.
  • Appliquer des permissions strictes sur le webroot : le compte FTP ne devrait jamais avoir les droits d'écriture nécessaires pour y déposer un fichier exécutable par le serveur web.
  • Séparer les comptes de service (FTP, Apache/PHP) pour qu'une compromission de l'un ne donne pas directement accès en écriture aux fichiers servis par l'autre.
